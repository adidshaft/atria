## 1. Fix now — confirmed bugs

Ranked by user impact, then effort. Stress leads (steps has no real bug).

**High impact**

1. **STRESS pins at "Medium" all waking day.** Live awake HR is z-scored against the sleeping/resting baseline (SD floored at 3 bpm), so ordinary wakefulness saturates activation to 1.0 — the metric measures "awake vs asleep," not stress. `AtriaStressMonitor.swift:149, :218, :270-284, :232-246` (+ `Insights.swift:336-338`). Fix: stop z-scoring waking HR against the sleep-rest baseline — learn a separate awake low-motion HR reference (or widen the divisor / withhold a band when only awake HR supports it). **Effort: large.** Requires real-day validation; do not fabricate values.

2. **HR landscape explorer jumps ~1×/sec and wipes selection.** Every live sample changes `pointsKey`, firing `refreshSeries` which unconditionally calls `anchorChartToLatest` + `clearSelection`. `AtriaVitalsCollectionSections.swift:4454, :4721-4727` (key at `:1470-1484`). Fix: rebuild `series` only; skip re-anchor/clear when the user has an active selection or has scrolled off the leading edge. **Effort: small.**

3. **Strain & recovery combo chart renders empty.** Card is fed the single-day selected-period series (`.day` = 1 point) but the chart is built to plot a 7-day line; strain `LineMark` needs ≥2 contiguous points and has no `PointMark`, so the line vanishes and recovery shows one dot. `AtriaOverviewSections.swift:10200-10207` (providers `:9705-9715/:9662-9674`; chart `AtriaStrainRecoveryComboChart.swift:95-157`). Fix: feed a multi-day slice (e.g. `.week`) and add a `PointMark` to strain. **Effort: small.**

4. **Sleep-detected review notification never fires while suspended.** `makeSleepReviewDecision` runs only inside `schedule()`, reached only from foreground/launch; the overnight BGTask handler never calls it — so the banner "only appears after opening the app." `LocalNotificationScheduler.swift:1113-1114, :1431-1558`; handler `AtriaApp.swift:466-549`. Fix: invoke a trimmed background sleep-review pass in `handleBackgroundTask` after maintenance/auto-confirm. **Effort: medium.** (Confidence medium; sound only once overnight auto-confirm actually runs — see §5.)

**Medium impact**

5. **Charts color-bleed:** the overnight "Heart-rate load" `AreaMark` gradient has no `.clipped()` (unlike every other AreaMark chart) and caption text sits directly below it in the same card. `AtriaHealthScreen.swift:2524-2608`. Fix: append `.clipped()` after `.frame(height: 156)` at `:2608`. **Effort: trivial.**

6. **Centered-pointer summary strip [SHARED — rings + sleep + charts clusters].** The Latest/Avg/Range rail sets pointer position to `0.5` whenever the window is flat/single-point (`spread == 0`), asserting a false "middle of range." Shared component behind the strain-ring, sleep-ring, and recovery strips. `AtriaOverviewSections.swift:12368` (rail `:12843-12867`, mounted `:10947`); default range `.day` = one point (`AtriaTrendChart.swift:2708-2715`). Fix: mount `AtriaDetailPeriodSummaryStrip` only when `points.count >= 2`, or gate `summaryRangeRail` + the Range mini-stat on a real `hasSpread` flag. **Effort: small.** (Also see §4 for the deeper "re-anchor to a meaningful band" polish.)

7. **STRESS gauge/timeline show 3.0 ("High") while label says "Medium."** Store caps only the level (`:680`) but publishes uncapped `rawActivation` (`:714`); the detail `score` (`rawActivation*3`) is never capped. `AtriaStressDetailView.swift:20-22, :76-81`. Fix: cap displayed score to the band ceiling when `!hrvAvailable` (or cap `rawActivation` in the store like the level). **Effort: small.** Resolving this + #1 also fixes the "flat line at 3.0" (chart itself is correct — stress F3).

8. **Morning/evening journal check-ins armed only from foreground.** Only caller is the scene-active block in `AtriaHomeView.swift:4262-4286`; a day with no foreground leaves the next morning's honest no-metric nudge unarmed. Fix: also arm them from `performBackgroundMaintenance`/`handleBackgroundTask` (idempotent via `scheduledDayKey`). **Effort: small.** (Confidence medium.)

9. **STRESS sleep-pause is dead code + stale tile.** `hasActiveSleepEvidence` is hardcoded `false` at both feed sites, so the documented sleep suppression never engages; the compact hero tile has no freshness gating, so a last-daytime "Medium" persists overnight. `AtriaHomeView.swift:10113-10124, :9434-9443, :10695`. Fix: wire a real active-sleep authority into `updateSharedStress`, and degrade the tile to a "last reading" qualifier when stale (mirror `AtriaStressReadingFreshness` already used in detail). **Effort: medium.** (Confidence medium.)

## Appendix — raw per-cluster findings

### Cluster: steps
- **[honest_by_design · highconf · highimpact · small]** The archive projection AtriaHistoricalDailyConsumerProjection.stepDays can NEVER produce a strap step count for a fully-drained past day: it returns state=.missing, stepCount=nil, knownStepDeltaSum=0, knownCoverageSeconds=0 for every civil day, regardless of how complete the drain is. Two independent reasons make this structural, not a data issue.
  - evidence: In stepDays the accept guard is `guard epoch.start >= day.start, epoch.end <= day.end, epoch.measurementValidated, let delta = epoch.stepDelta, delta >= 0 else { rejected += 1; continue }` (AtriaHistoricalDailyConsumerProjection.swift:562-570). Every historical-gravity epoch's stepDelta is nil: the aggregate builder sets `stepDelta: AtriaHistoricalStepRecovery.stepDeltaFromHistoricalGravity()` (AtriaHistoricalAggregateBuilder.swift:439) and that function is `static func stepDeltaFromHistoricalGravity() -> Int? { nil }` (AtriaHistoricalStepRecovery.swift:100, with the file header stating WHOOP4 0x2f rows are '~1 Hz gravity... never step evidence here'). So `accepted` is always empty, and separately `fullyCovered = accepted.first?.0.start == day.start && accepted.last?.0.end == day.end && zip(...).allSatisfy { $0.0.0.end == $0.1.0.start } && knownSeconds == daySeconds` (lines 589-592) requires gapless midnight-to-next-midnight coverage of all 86400s.
  - location: `Atria/Atria/AtriaHistoricalDailyConsumerProjection.swift:562-605; Atria/Atria/AtriaHistoricalAggregateBuilder.swift:439; Atria/Atria/AtriaHistoricalStepRecovery.swift:9-100`
  - fix: No change to the projection and NO fabrication: fullyCovered is correct and 1Hz gravity is genuinely not step-capable through this path. The user-facing expectation ('drain backlog -> past days fill with steps') is only satisfiable via the separate gravity-cadence receipt path (see next finding). Even hypothetically populating stepDelta would not help, because a real worn day never emits validated epochs that are contiguous from exact civil midnight to exact next midnight with zero gaps. Document that the archive projection is intentionally not the step source.
- **[feature_request · mediumconf · highimpact · medium]** Real strap step counts come ONLY from AtriaWhoop4GravityCadenceStepModel receipts saved in AtriaWhoop4MotionTickDailyStore, and those are computed windowed to the CURRENT physiological cycle only ([cycleStart, now]) and are deferred while a backlog drain / exact-recovery lane owns the archive. There is no backfill that recomputes a step receipt for a PAST cycle after the backlog catches up, so a prior day that never got a live receipt stays empty forever. This — not the archive projection — is why 'steps still show nothing / not fresh after catch-up.'
  - evidence: Receipt computation is windowed to the open cycle: `HistoricalArchive.motionTickDayEvidenceRead(start: cycleStart, end: now, ...)` then `AtriaWhoop4MotionTickDailyStore.shared.save(evidence, ...)` (Sessions.swift:8107-8162). While draining it is skipped: `guard !HistoricalArchive.exactRecoveryProjectionOwnsArchivePriority() else { ... currentCycleStepReceiptDeferredUntilForeground = true ... return }` (Sessions.swift:7815-7826). Prior-day rows are only re-read from previously saved receipts: `AtriaWhoop4MotionTickDailyStore.shared.recentReceipts(strapIdentifier:, limit: 14)` with priors filtered to windowEnd <= wake boundary (Sessions.swift:7645-7669); mergingCurrentCycleReceipt only admits the exact current window or a contained-in-current receipt (AtriaWhoop4MotionTickDailyStore.swift:327-392). No call recomputes motionTickDayEvidenceRead for a closed past-cycle window.
  - location: `Atria/Atria/Sessions.swift:7761-7826, 8083-8203, 7645-7669; Atria/Atria/AtriaWhoop4MotionTickDailyStore.swift:300-392; Atria/Atria/HistoricalArchive.swift:2661-2712`
  - fix: Add a bounded past-cycle receipt backfill, gated on AtriaWhoop4GravityCadenceStepModel.releaseDailyAuthorityQualified and only when exactRecoveryProjectionOwnsArchivePriority() is false (drain settled): for each recent physiological-day window in the last ~14 days that has no store receipt, call HistoricalArchive.motionTickDayEvidenceRead(start: dayStart, end: dayEnd, ...) windowed to that single day (same windowed decode already used for the current cycle, so no whole-archive reopen / no memory balloon) and save() the result. Needs device/data to confirm how many recent days currently lack receipts vs legitimately have no qualified cadence.

### Cluster: stress
- **[real_bug · highconf · highimpact · large]** Stress pins at 'Medium' all waking day because live awake HR is z-scored against the sleeping/resting baseline (tiny SD, floored at 3 bpm), so ordinary wakefulness saturates the activation to 1.0.
  - evidence: hrActivationFraction computes hrZ = (hrNow - restingStats.mean) / max(restingStats.sd, 3.0) then clamp01(max(hrZ,0)/3). restingStats.mean/sd come from freshSamples(...).restingHR — one canonical LOWEST resting window per day (Insights.swift canonicalDailySamples/restingStats), i.e. an overnight/resting distribution with mean ~resting and only a few bpm between-day SD. A normal awake HR of 80 vs resting 60 gives hrZ=(80-60)/3=6.7 → /3 → clamp 1.0. band(1.0)=3 (High), capped to Medium in HR-only mode (line 245). Even full HR+HRV mode floors activation at 0.6*1.0=0.6 (line 235), which is already the Medium band. Test testHRVOnlyModeCapsEmittedLevelAtMedium explicitly feeds hrNow=80/rest=60 and asserts .medium with the comment 'HR alone can push activation to 1.0' — the pinned-Medium behavior is currently encoded as intended, but it means the metric measures 'awake vs asleep', not stress.
  - location: `Atria/Atria/AtriaStressMonitor.swift:149 (hrActivationFloorSD=3.0), :218 & :270-284 (hrActivationFraction), :232-246 (combine + HR-only Medium cap); Atria/Atria/Insights.swift:336-338 (restingStats = daily resting HRs) ; corroborating test Atria/AtriaTests/AtriaStressMonitorTests.swift:198-223`
  - fix: Stop z-scoring waking HR against the sleeping-rest baseline. Concrete options, all requiring real-day validation (never fabricate a value): (a) learn a separate personal AWAKE low-motion HR reference and normalize against that; (b) replace the /3 z-divisor and 3bpm SD floor with a wider, circadian/orthostatic-aware scale so sitting-upright elevation is not top-of-scale; or (c) mirror the existing sleep-pause honesty — withhold a numeric band above Calm/Low when the only evidence is awake HR elevation with no HRV corroboration. The per-person calibration the user asks for partly exists (PersonalBaseline resting+HRV) but there is NO awake-HR reference, which is the missing piece.
- **[real_bug · highconf · mediumimpact · small]** The detail gauge and timeline plot the UNCAPPED activation (rawActivation*3), so in HR-only mode they show 3.0 (the 'High' end of the dial) while the label is capped to 'Medium' — an internal contradiction.
  - evidence: The store caps only the LEVEL (cappedBand = min(smoothedBand, .medium) at line 680) but publishes the uncapped EMA as rawActivation (line 714). AtriaStressDetailInput.score returns min(max(state.rawActivation*3,0),3) with no cap, and the timeline AtriaStressDetailReading(historyPoint:) uses activation*3. So when activation saturates at 1.0, the hero gauge needle and the timeline sit at 3.0 (the tick literally labeled 'High') while state.level is Medium and the text says 'Medium'. This is exactly the reported 'label medium but line flat at 3.0'.
  - location: `Atria/Atria/AtriaStressDetailView.swift:20-22 (historyPoint score=activation*3), :76-81 (input.score = rawActivation*3, uncapped), :616-642 (gauge draws score with Calm/Medium/High ticks); Atria/Atria/AtriaStressMonitor.swift:680 (level capped) vs :711-714 (finalState.rawActivation = uncapped ema)`
  - fix: Make displayed magnitude agree with the emitted band. Either cap the displayed score in HR-only mode (e.g. in AtriaStressDetailInput.score clamp to the band ceiling when !state.hrvAvailable), or better, cap rawActivation in the store when hrvAvailable==false the same way the level is capped at line 680, so every downstream surface (gauge, timeline, history) never exceeds the band the label claims.
- **[honest_by_design · highconf · lowimpact · trivial]** The detail timeline is NOT a hardcoded constant series and is not a single-value viz bug — it plots real per-reading activation; it reads flat at 3.0 only because the underlying activation is genuinely saturated (Finding 1).

## Stress rescoring — adversarial review outcome (2026-08-08)

The awake-referenced rescoring (299c426a) was adversarially reviewed (4 lenses).
Verdict: direction right, first cut not shippable. Fixed in the follow-up commit:
- **B1** noisy-OR replaced with a symmetric-weight corroboration model
  (`stressCorroborationWeight` 0.6): a lone HR OR lone HRV signal caps at Medium;
  only both together reach High. Kills HR-alone→High (contract break),
  lone-HRV→High, and moderate+moderate→High.
- **B2/#9 (partial)** awake buffer now admits only quiet-awake HR
  (`> rest + 8` and `<= rest + 40`, zone < 2), so overnight sleeping HR can no
  longer collapse the learned reference and cause the post-wake false Medium.
- **B4** buffer append now mirrors the scorer's activity exclusions.
- **B6** file header, scored narrative, chip, and AtriaAboutMetricSheet copy
  rewritten to describe awake-reference + corroboration (were factually wrong).

**KNOWN LIMITATIONS still open (documented, not silently shipped):**
- **B3 — sustained stress absorption.** The awake reference is a 45-min trailing
  median, so a genuine sustained stressor (>~15-30 min) is gradually absorbed
  into the reference and drifts toward Calm. Real fix: a slower multi-day /
  sleep-gated awake baseline (PersonalBaseline-style tiers) or a slow EMA, plus
  an absolute-elevation term. The quiet-awake buffer filter mitigates but does
  not eliminate this. HR-only mode (the common state pre-HRV-trust) has no HRV
  term to hold the band up, so the miss is largest there.
- **B5 — workout-suppression cliff.** `hrNow > rest + 40` returns `.active`
  (no level) while the rescored HR term can read High just below that boundary,
  and it anchors to rest while the HR term anchors to awake HR. Pre-existing
  heuristic, now more consequential. Fix: require a second activity signal
  (isRecording / zone≥2 / cadence / sustained duration, not one sample) before
  suppressing, and scale the delta to the awake reference.
- **#9 (scoring-during-sleep).** `hasActiveSleepEvidence` is still hardcoded
  false at both callers (AtriaHomeView.swift:10123/:9443), so the store still
  SCORES/records stress bands during sleep. The buffer filter stops sleep from
  contaminating the awake reference, but wiring a real active-sleep authority (or
  a low-HR proxy) into those two call sites is the proper fix and remains open.
- **Minors:** persist the awake reference across launches; blend learned→default
  spread (floor 5 vs default 12 step-change); scope the ~65/20 validation claim
  to the HR-only path; cold-start offset/spread don't scale with fitness.
